# 性能差距诊断

直接调用时，从用户给出的版本、实际入口、比较表或已确认的目标开始。把实测已确认的相对退步或目标缺口列入第 1 步。只有排名或证据不足时，说明还缺哪个同义对照或目标数据。已有可确认的场景先查。

从 `$optimize-project-performance` 转入时，直接接续同一版本、同一份记录和用户已给的选版答复。两种入口都沿用原测量协议、执行权限、总预算、累计时间及各项剩余复测次数。项目要求的独立复测仍按原协议执行。未确认的收益幅度例外保留为待定，其他诊断继续。

**第 1 步只做一次。每条行动链都在第 2 至 5 步内完成，终点只回答“当前有无明确值得尝试的优化方案”。** 第 2 步选定要解释的差距，第 3 步可连续做多项核查，有候选时到第 4 步查复用范围，第 5 步结算并选下一项。允许一条链覆盖多个场景，也允许同一场景有不同的待解问题。

每一步用 **判断｜依据｜下一步** 留下一行记录。要进一步核查时，先写清“固定什么、改变什么、哪些可观察结果会让决定不同”，再查已有证据。原记录能决定下一步就直接引用。只要求分析时，交付核查方法和各结果对应的决定。需要新试验时，在已有执行授权和预算内进行，并把实际观察写回原行。

## 1　一次建表，区分退步与目标缺口

在原记录内核对实际测过的工件、比较表和产生负载的程序。已有慢项清单就直接续用。多棵源码、不同计时入口或本地改过的依赖按运行收据对齐。保留入口、输入规模、输出语义、运行条件和每一轮的原判定。

| 场景进入的依据 | 需要保留的证据 |
| --- | --- |
| 相对退步 | 同义比较的基线与所选工件、同期两侧绝对值及相对差、协议门槛和失败轮次。百分比和绝对差取自同一组比较，多个门槛命中同一比较只计一次。 |
| 已确认目标未达 | 目标的来源、指标方向、单位、负载、实测值与距目标的差额。相对目标沿用指定参照，绝对目标可单看选定工件的实测。耗时上限算超出多少，吞吐下限算还差多少，资源上限沿用原单位。用改动前的工件验证下一次试验能减少多少差距。 |
| 两项都成立 | 同一场景 ID 挂两条依据，各自保留原成绩。追平基线后仍差目标时，只关闭已追回的那部分。 |

同一场景在不同工件、参照或轮次上的证据挂回原行。队列按两类确认场景的并集去重，分别报告相对退步的比较数和未达目标的场景数。只命中目标的场景进入第 2 步，回归数可为零。错配、缺测或统计未明留在原行。只剩这类问题时，交付证据缺口及能改变判断的最小核查。需要设计或执行该测量时使用 `$noise-resilient-benchmarking`，整轮优化按主流程④的补证与停止条件处理。

## 2　选本轮主项，明确还有哪一段没有解释

从原排序选第一项仍可推进的场景。固定本轮的输入、出口、运行条件、要解释的差距及适用参照。查看此前轮次在这项上已经解释了什么，是否还有另一规模、运行时、分支或成本阶段待查。

开始时写下这条链的有限边界。项目已有的预算、期限和复测次数按原口径累计。纯分析且没有数值限额时，根据当前材料列出有限的核查动作，每完成一项就划去一项。新线索可以替换剩余动作，清单用完即结算。给同一问题改名或改选主项都不刷新已用额度。

**本步判断**　写明“本轮解释哪个差距，哪些已有结论可以引用，剩下要查什么”。同义对照证实了退步，或实测证实未达确认目标，就进第 3 步。遇到以下情况，先处置对应比较。

| 比较的判断 | 先做的核查 | 依据结果决定 |
| --- | --- | --- |
| 比较口径有误或输出语义不同 | 对齐实际加载版本、输入、输出、工作量和计时边界，找出能回答原问题的同义对照。若当前输出违反契约，先处理正确性。 | 同义对照仍超限就进第 3 步，当前版本在该范围已达标就回填。若两个版本按设计就做不同的事，只关闭原比较。新行为有既定性能要求时另找同义参照。 |
| 证据不足或不同测量方向相反 | 保留各轮数据，找出一个可能改变结果的条件，例如输入规模、计时范围或进程状态。先核对原记录，必要时按原协议有限补证。 | 差异随条件稳定出现就分开判。按原协议证实超限的条件进第 3 步，证实达标的范围回填。同版本同条件的可信结果仍冲突，则保留双方，写明还缺什么，继续其他项。 |
| 当前版本可能已经恢复 | 核对实际工件是否含修复，再按原基线或确认目标，复核相同入口、输入、运行条件和保护。 | 只关闭该版本已恢复的范围，保留旧成绩。同一场景若仍差目标，继续追查。历史候选的收益须补当前工件证据。 |

## 3　解释主项，判断额外成本从哪里来、如何局部改变

先从负载的实际构造追到计时入口和当前源码分支，核对会使它走另一条路的条件。例如判定长短可能用解码后的长度，派发可能先命中基类。选出能改变决定的核查，写下新增事实或排除的解释。若同一动作只会重述已有结论，转入第 4 或第 5 步。协议规定的独立复测按原要求处理。

| 顺序 | 思考方向 | 需要给出的判断 |
| --- | --- | --- |
| ① 看规模 | 小、中、大输入以及原本较快的规模分别怎样变化？ | 优先查一次性准备、逐项工作、等待还是结果交付。标明哪些解释仍可能成立。 |
| ② 定契约 | 各出口实际需要什么？已有或拟议的快法在哪个最小反例上会改变结果、顺序或异常？ | 区分必须保留的工作与可能省掉的工作。 |
| ③ 追调用 | 当前工件在同一负载做了什么，有直接基线时两版分别做了什么？动作是每次调用一次、每列一次，还是每元素一次？ | 写明会消除的动作及次数。两版都承担的成本仍可能值得优化，把它列为减少现有耗时的机会。要把它列作退步原因，另给能解释两版差距的证据。 |
| ④ 验假设 | 按当前慢项可能多花的那一步，在同一份项目记录中查以前验证过的优化做法。哪些入口用过，在哪里失败？哪个同输出对照能区分解释？ | 对照当前源码与最接近的已采用或已拒绝写法。若重试，指出新落点、适用条件或隔离手段具体改变了什么，列原来失败的保护项。缺少实质差异时引用旧试验并换方向。 |
| ⑤ 查代价转移 | 哪些调用者共用改动位置？不走拟议快路的调用者是否也会多付一次分支、调用或分配？ | 列出原本通过但需联测的保护项。一次试验改了多处时，注明还需隔离哪处。 |
| ⑥ 定边界 | 在哪些条件下可选一次路径、每项少做什么、哪些检查必须逐项执行、失效后回到哪条路径？ | 给出可被反例推翻的局部方案、直接对照和采用／回退条件。 |

### 根据分析结论选择下一步

在原表依次回答 **差距依据是什么 → 能解释多少 → 哪个改法值得一试**。两版原本都有的成本可能值得消除。若把它列作新增退步的原因，要说明为什么同一负载在两版走法或代价不同。对耗时差可用“需追回的时间 ÷ 可省的次数”估算每次至少须省多少。标明这是所需收益，实际收益仍待测。隔离试验既查动作是否减少，也测用户指定的入口指标。目标为吞吐或内存时，用相同工作量复验对应指标。只有诊断办法时先记录诊断。保留与释放对象、回调、异常和中断等会被调用者观察到的先后关系，给最可能破坏它的反例。

| 已有判断 | 最能区分结果的下一步 | 依据结果决定 |
| --- | --- | --- |
| 有一个明确改法 | 指出会少做的具体动作、调用点和失效条件，设计只改这一处的可回退对照，同时检查目标入口与受影响的相邻调用。 | 可预测动作和结果时就可列候选。已有有效试验时，目标改善且保护满足就按第 5 步判定。动作确已省掉而收益上限仍太小，停止这一写法，回查剩余差距。 |
| 有几种可行改法 | 比较每种写法会省什么、会影响谁。先选一个能区分原因、改动小且可回退的方案，各方案使用同一起点。 | 简单方案已满足目标和保护即可停止比较。只在某些条件有效，就收窄方案。还有明确缺口，再试能解决该缺口的另一种。 |
| 已有方案可能覆盖 | 核对本项是否经过同一成本位置、满足同一适用和失效条件。分别核对方案是否已进入当前版本、本项是否已有适用的实测。 | 前提吻合就引用原方案，只补当前入口缺的必要证据。当前已达标可关闭该范围。若该动作已省去仍慢，就保留已证收益，追查剩余成本。分支或前提不符则跳过这个方案，继续本项追因。 |
| 差距可信，原因未定 | 写出相互竞争的解释及各自的预测。例如在读取与结果组装之间，先保持组装方式相同，只去掉一次疑似重复读取，检查读取次数和整个入口的耗时。 | 次数减少且目标差距缩小，就沿读取路径分析。次数已降而差距仍在，且精度足以排除预期收益，就转查组装或其他成本。仍分不清时，换一种有区分力的核查或列待补证。 |
| 只解释了部分差距 | 按规模、运行条件或成本阶段拆开，对各部分分别看目标差距。拟按规模分流时，连同新分支的成本检查边界两侧。 | 已达标的范围关闭，只把受益范围关联到方案。对适用基线或已确认目标仍有差距的部分保留在队列中，同一场景的不同原因仍挂在原行。 |
| 主要成本疑在另一阶段或依赖 | 对同一输入串起内部阶段和公开入口，再只改变怀疑的环节，例如保留原生写入与输出内容，只换结果组装方式。 | 端到端差距随该环节变化，就转向该处。当前层的微调可结束，公开入口尚存的缺口继续跟踪。只有热点、缺乏区分证据时继续追因。超出范围就记录负责组件和诊断入口。 |
| 成本涉及必要保证，现有捷径不安全 | 用最小反例检验输出、异常、所有权或并发保证，再找保留保证的等价做法，例如只在仍有效的范围内复用检查结果。 | 等价做法能省工作就列候选。反例成立就淘汰该捷径。已查替代均无效时，保留保证并记录已查范围。仍有硬性缺口就换方向，确需改变契约时提交取舍。 |
| 局部微调收益上限可能太低 | 用可归因的关键路径耗时或隔离对照，估算该处即使完全消除最多能省多少，与目标还差的绝对耗时及可选收益价值相比。并行或重叠的时间只计一次。 | 有独立价值的部分可作候选并保留剩余差距。上限太小且这部分没有单独采用价值就结束局部微调。硬性缺口转查算法、数据布局或调用方式。上限未知时先补定位证据。 |

**进入第 4 步的条件**　已经形成值得尝试的具体改法或找到可复用的同一方案。只得到定位、排除或口径更正时，有可推进的核查就留在第 2 或第 3 步。达到本链停止条件就直接去第 5 步。一次否定只约束该写法和已查条件。

## 4　逐项匹配，判断哪些慢项适用这个方案

按调用点、分支和数据有效期在原清单中找关联项。按场景族找待核对项，再把方案前提与每项实际退步或未达目标时的负载、运行时及出口相交。列清哪些调用者真的省掉动作、哪些只会承担新分支的开销。共享一个函数或类型名只足以列为待核对线索。其他输入可能也执行同一动作，但只执行一次、已达标或每次成本太小，可留作保护或局部线索。每个场景可保留一个主结论和其他方案的关联，同一组合只检查一次。

| 判断 | 处理 |
| --- | --- |
| 同一改动可复用 | 逐项确认该场景经过相同成本位置，当前输入满足相同前提，退出与保护条件也相容。引用同一方案，写明覆盖的比较条件。 |
| 只覆盖一部分 | 关联已解释的部分，明确剩余分支、运行条件或成本阶段。剩余问题保持在队列中。 |
| 可借用思路，具体改动不同 | 记下不同的调用点和已有线索。已有局部证据足够时另列方案，否则保留为下一轮主项。 |
| 本方案不适用或尚无依据 | 只结束“这个场景 × 这个方案”的匹配。场景继续按原排序接受其他解释。 |

原本通过但会受影响的调用者登记为保护项，单列在慢项计数之外。一次试验同时改了快路和共用循环时，观察到的总体差值只归该次组合。若要归到具体动作，用保留相同输出、只改该动作的对照。给每次匹配记下场景、方案、适用条件和证据版本。同一组合已有肯定或否定判断时直接引用。出现新分支、新前提或新证据时才重开这次匹配。

## 5　回填并决定下一轮

沿用同一张场景表，每项记录 **场景 ID、原始比较或已确认目标、实测值与差距、已解释范围、行动链的二元结论及理由、方案引用、剩余问题、下一证据和分析状态**。方案说明只写一次，列出原因、改动点、适用／失效条件、保护项、验证方法和证据状态。一个场景可引用多个方案，一个方案可被多个场景引用。

**去重以三个对象为准。**

- **场景**按 ID 计数。跨轮补充原因或关联方案时更新原行。不同入口、规模和比较条件保留各自的证据。
- **方案**按实际改动点、要省的工作和成立条件判断是否相同。同一位置的不同分支、相反的输出约束或不同的失效条件要区分。收益可能重叠时，以组合工件的直接对照判定整体收益。
- **验证**可在同一工件、对照、输入、指标和计时条件均匹配时复用。一组联测可以服务多个方案，每个场景仍保留自己的结果和原协议要求的独立复测。

**有方案时落实试验。** 留下初判“值得试”、最接近旧试法的反证、本次不同的改动点、预期少做的动作、能击穿前提的输入，以及目标和旁路的保留或撤回条件。只要求分析时，到这里交付可执行的试验设计。已有实施授权且试验和收尾均装得进余额时，在同义输入上隔离试验，验证目标和相邻保护项。需要组合选版时，按 `$optimize-project-performance` 第④、⑤步的共用规则复验并交付。把实测后采用、收窄、撤回或未明写回同一方案。对直接父版的增量、对原基线的退步和对已确认目标的剩余差距分别更新。区间仍容许有价值收益时保留未明。能以足够精度排除收益时，关闭该写法。若另有独立假设，在原链剩余额度内回第 3 步。

### 每条行动链只交付两个结论之一

| 结论 | 何时成立 | 写回原行 |
| --- | --- | --- |
| **有明确值得尝试的优化方案** | 能定位真实负载走到的代码、相对现实现能省的动作、预期影响和试验成本。最接近的旧试法已被考虑，关键语义有保法。 | 每个独立方案只写一次。列出试验与直接对照、一个能击穿适用前提的输入、目标和相邻保护、保留与放弃条件。注明新方案待验证，安排顺序按现有证据和成本决定。 |
| **当前没有值得尝试的优化方案** | 在本轮已核查的条件下没有改法达到推荐标准。例如已达标、不可比、最接近的改法已有反证、可选收益太低，或仍缺定位证据。 | 指明具体排除了哪条路，还有什么未明。已有失败结果可以结束该写法。保留原成绩、获批例外及范围。只有能指出什么新增观察会改变判定时，才列相应补证动作。 |

判断可选收益时，结合每次绝对耗时、已知调用频率及实现维护成本，按项目认可的价值标准取舍。频率未知就保留未知。一个成立的候选已经足以给本链判“有”。淘汰一个写法后，若还有基于现有证据、在本链边界内可做的其他核查，就继续判断后再结算。

**防止重复进入同一条链。** 下一动作若在同一场景、同一成本假设、同一对照和同一版本证据下已经做过，就引用原结果。到达本链边界，或已找不到会改变结论的未做动作，就在第 5 步作出二元判定，把该链移出本轮待办，按原排序转下一项。只在新证据、实际条件变化或原来不可行的区分性核查变得可行时重开对应范围，沿用原记录和已用额度。单纯多想一种说法或再等一轮不构成重开条件。

**覆盖进度根据剩余问题单独填写。** 还有未经检查或能继续推进的独立范围，记“仍待分析”。已查至本轮边界，仍缺会改变推荐判断的特定证据，记“已检查，待补证”，写明重开条件。其余记“已完成分析”。“全部适用判据已满足，所以无方案”可完成，“一条有候选、另一条尚缺分段证据”可已检查待补证。只待候选本身实测、排期或采用时写方案备注。批量汇总时逐项核对判定与进度的依据。

同一场景有多条链时，保留每条链的结论和作用范围。任一条有候选即可交接该方案，剩余独立范围继续按原排序核查。场景全部必要范围结算后，只计一次，有候选归“有”，各链均无候选才归“无”。用同一份清单核对覆盖。组合换版后，本场景的新结果挂回原行。只对新选定工件上确实新增的已确认差距补行，记录首次进入的版本，保留已结算项的历史。

```text
受理场景总数（退步与目标缺口按 ID 去重）= 已完成分析 + 已检查待补证 + 仍待分析
已完成分析 + 已检查待补证 = 判有的场景数 + 判无的场景数
```

**还有获准、可推进且装得进余额的慢项，就从第 5 步回到第 2 步。** 全部已结算、只剩等新证据的项，或预算与权限到界时，在原记录留下所选工件、保护结果、各链结论、未查范围及恢复条件。独立诊断将这些结果交给用户，整轮优化交回主 Skill 选版与交付。只有已结算的链填二元结论。下一阶段沿用已用时间和次数，已经排除且没有新证据的试法继续关闭。

## 同一套判断会得到哪些结果

- **有明确值得尝试的优化方案。** 在 `ab794d1` 的 CP312 原生 Escape 上，对旧功能基线 B0，单项 `dict.items()` 已快，百项和千项的差距却随规模扩大，千项独立轮每次多耗 30.49 µs。沿循环查到每处理一项都要取出、放回迭代器并留值以备重读。旧快法经映射调用 `values()`，可能触发字典子类覆写。候选让单向循环持续持有迭代器，从真实键值对取值，使这条路径保持原值语义。只关联到 MySQL 只取值、调用方单向消费的真实键值视图。用普通容器、JSON 键值对、需要重读及回调修改字典的场景验证输出和首个异常。交接时该写法仍待实测。
- **当前没有值得尝试的优化方案。** 同一版本的 CP313 万项整数对新语义参照 F0，公开 JSON 每次多耗约 109 µs，同一输入进 SQL 却少耗约 73 µs。另对诊断参照 C7 缩小分组，仍能复现公开入口退步，单输入采样却无法区分运行上下文和结果组装的代价。保留原退步，记“已检查，待补证”，转下一项。只有能区分这两个解释的新对照才重开此链。
- **只差用户目标也能开始。** 假设同一批任务从 500 ms 降到 220 ms，确认上限是 150 ms。登记一个目标缺口 70 ms，相对退步记零。用 220 ms 这版对照下一项改动，同时核对 150 ms 的目标。若这个场景原准复测 3 次、已用 2 次，本轮仍只余 1 次，是否能开试验还要算入收尾时间。

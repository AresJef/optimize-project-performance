# 项目运行性能优化

整轮优化从这里开始，由本入口选择并交付一个经过验证的版本。用户调用本 Skill 后，Agent 在下文条件成立时自行打开并遵循对应的专项入口，随后回到当前任务。按下文链接读取同版文件。若宿主将入口分开放置，按给出的调用名定位同版 Skill。

## 启动时先问用户怎样选版

每次开始新的优化任务，第一条回复就向用户提出下面的二选一。无论用户是否给了性能目标，或是否带来了第一轮实测结果，都先明确本次选择。如果用户已在本次请求中明确回答，就复述并记录该选择。

> 假设一项改动在正式测试和独立复测里，每轮都比原版快，保守估计也有实际收益。只是有的轮次快得多，有的快得少，提速幅度的波动超过了项目标准。其他要求都达标。你希望最终版本怎么处理这项改动？
>
> - **接受**　先和其他改动合在一起复验。如果组合后仍能确认提速，其他要求也都达标，就把它保留在最终版本里，并如实报告各轮的提速范围。
> - **不接受**　按原来的全部标准选版。只要提速幅度的稳定性没达标，就把这项改动排除在最终版本之外。

把答复和适用范围写进同一份项目记录。这个选择决定哪些改动可以入选，分析、测量、改代码或发布各按任务原有权限执行。通用实施授权和其他任务的答复都不能代替本次选择。同一任务续接或进入慢项阶段时沿用已记录的答复。

尚无明确答复时记“待决定”，继续不依赖该选择的已获准工作。若遇到只有按这条例外才能入选的改动，先单列待决定并保留实测记录，收到“接受”前不将它纳入最终组合。

## 选择起点和行动范围

1. **从哪里开始？** 整体提速从第一轮①开始。用户已经带来第一轮选定版本和测量记录时，先核对实际工件、范围清单、目标及证据。齐备就直接在本入口判断是否还有慢项。只有候选跑分或慢项排名时，先补影响判定的事实。
2. **这次可以做到哪里？** 按用户请求和已有授权确定分析、测量、改动及采用版本的范围。只要求分析或规划时，用已有证据交付判断、最小试验和停止条件。获准补测时，把实测结果写回对应场景。获准实施时，在预算内做可回退的试验，验证目标和保护项，在采用权限内交付一个经复验的版本。

例如，“全面分析整个库，先别改代码”从第一轮开始，交付全范围清单、有依据的候选和试验设计。一个场景受阻时，继续其他获准且可独立推进的项。

第一次需要设计或调整测量方案、测量原版或候选版本，或判断现有数据能否用于选版时，先读取 [Noise-Resilient Benchmarking](../noise-resilient-benchmarking/SKILL.md)（`$noise-resilient-benchmarking`）。带入实际版本、入口、目标、已有证据和剩余额度。已有批准的测法和适用证据时直接沿用。只做规划时，写清测法、成本以及必要的补证、独立复测和验收安排。实际采集与例外采用按本次授权执行。

把结论写回同一份记录，说明测的是哪个版本和场景、与谁比较或要达到什么目标、结果能说明什么、还缺什么。主流程据此决定是否扩大试验、收窄改动、撤回或交付。

## 第一轮　全面优化

### ① 固定起点，建立清单

从公开接口、支持矩阵、规格、使用示例和实际部署中确定承诺的范围。给每项能力一个稳定 ID，例如一种格式、一个 API、一条批处理或一项服务操作。原本很快、缺少独立基准、只在特定条件启用、按契约拒绝的能力也要登记。先做低成本的全范围盘点，把深入调查留给有成本证据的路径。

固定实际可用的起点，包括源码或配置、构建或部署、真正加载的版本、环境和回退点。原版或旧功能的固定参照用来判断原差距，最近已验的工作版本用来判断本次改动增量。新能力若无旧版可比，登记自己的起点或已约定的绝对目标。

**先分清用户有没有给出可验证的项目目标。** 可验证意味着知道哪个用户操作、在什么条件下、按什么观察作决定。目标可以是绝对上限，也可以是同一负载相对起点可靠变快。并非每个目标都需要一个百分比。

| 用户输入 | Agent 应做什么 | 采用和汇报依据 |
| --- | --- | --- |
| **已提供可验证目标**，或用户明确指定一份验收合同 | 把目标按原意记下，注明来源、入口、负载、指标、阈值或比较准则、必须保护的行为和资源约束。先在起点跑一遍，确认测量覆盖了用户关心的完整操作。只澄清会改变判断的歧义。 | 以用户给定的目标验收，同时报告实际改善和代价。目标既已满足时，记录达标事实，继续哪些优化由原任务范围决定。未达到的硬目标保留原差距。 |
| **未提供可验证目标**，例如只说“把项目跑快” | 先查项目是否已有对本次范围有效的批准标准。有则记录为“沿用项目既有目标”，说明适用范围。没有则从实际用法、样例、调用记录或已有故障选一个主要入口和代表负载。写出“建议目标”、选择依据、保护项、怎样区分有无改善，以及哪些实际使用情况未知。能取得同义起点就先测。 | 将建议标为“推定，待确认”。在已授权范围内可以做可逆试验。目标明确为尽力改善、结果在所声明负载上可靠、必要保护均满足且权限允许时，可交付实测改善的一个版本，并把推定写明。需正式验收而用户尚未委托制定目标时，把建议目标、负载和保护项用一句话请用户确认。用户明确委托 Agent 制定目标时，记录授权和选定的判据后执行。只将用户接受或已有授权覆盖的目标用于正式验收。若取舍足以改变选版，向用户提出一个带具体收益和代价的问题，决定前保留已验证检查点。 |
| **只提供一部分**，或不同目标的优先级未明 | 已明确的指标及约束照用。仅将缺失的负载、阈值、优先级或容忍范围列为待定，给可执行的默认方案与理由。用户已委托的普通技术选择可直接进行。 | 已明确项按原标准判定，推定项另报。需要放宽既定保护、牺牲一项业务换另一项时，沿用已批准的取舍权限，权限不足就只询问该决定。 |

**把目标落到一次真实调用。** 交互功能可观察端到端响应和尾部延迟，批任务可观察完成相同工作量的总耗时，持续服务可观察规定负载下的成功吞吐、超时与积压。内存、能源或成本是目标时使用对应指标。区分冷启动和常驻调用，给主要目标配上实际会受影响的保护项。说明是用户明确、项目已批准，还是 Agent 根据样例推定。缺少使用频率时按场景呈现。

在现有记录里写一句“目标来源与确认状态｜哪个入口、哪份负载｜相对谁或达到什么值｜必须保护什么｜怎样验证”。如果既没有用户目标，也找不到能代表真实使用的入口或数据，先问用户最想改善的是哪次操作、通常处理多大规模。可以同时跑通基础用例，清楚标记其代表性尚待确认。

**退出条件。** 每项能力已有实际入口、起点、目标来源、必要保护和证据或缺口。对齐本次授权、已用时间与次数，预留必要验证和交付成本。无基准时，在可操作的权限内先跑通一次“调用、核对结果、计时、读回”。重要业务取舍尚未决定时，独立的起点测量和其他可逆工作仍可继续。

### ② 从用户症状追到实际瓶颈

从调用者发起操作，一直追到结果可用。逐段核对消费者真正需要的结果。哪些读取、分派、转换、分配、复制、往返或等待可以整步省去？这些工作是每次调用一次、每块一次、每行一次，还是每个元素一次？比较小、中、大输入和原本表现好的规模。已得事实只在同一拥有者、配置和有效期内复用，遇到换块、回调、并发写或状态变更时重新确认。

| 观察到的现象 | 最小的区分性核查 | 结果怎样改变下一步 |
| --- | --- | --- |
| CPU 忙，工作量放大后耗时增长过快 | 取代表调用的热点和动作计数，改变输入规模，检查重复遍历、算法复杂度、数据布局、格式转换或边界调用。 | 同一动作随规模重复，就隔离该动作。动作减少而公开入口没改善时，沿剩余关键路径查。 |
| 总耗时高，CPU 用量低或工作线程在等 | 用同一请求的时间点拆分排队、取连接、I/O、外部依赖和本地处理，核对调用次数、字节量与缓存状态。 | 往返次数主导时试批量或去重，等待集中在其他组件时跟到对应边界。本地写入更快只证明本地这一段。 |
| 并发提高后尾延迟急升，吞吐停滞或报错增多 | 固定到达轨迹和初始缓存，记录发出、成功、失败、超时、期末仍在途或积压。跟踪工作池、锁和下游占用。分别看单请求各段时间及总体分布。 | 识别排队还是下游等待后再试调度或分流。闭环客户负载与按时间发出的负载分别评价。成功请求的分位数无法说明仍在排队的请求，来自不同分布的分位数也不能直接相减归因。 |
| 峰值内存、分配或长时间运行后表现恶化 | 对同一工作量记录存活对象、分配／复制量、峰值和稳态，查缓存生命周期、GC、资源释放及命中率。 | 短命中间对象可尝试直接交付或有界复用。缓存增益伴随不可接受的内存、陈旧结果或并发代价时，缩小作用域或撤回。 |
| 内部函数快了，实际 API、命令或服务仍慢，或两个测量方向相反 | 将冷启动、解析、核心处理、结果组装与消费分开。固定同一输入和输出，一次只改变怀疑的阶段、负载分布或进程状态。 | 按有证据的条件分别判断。只能复现差距还不能定位原因时，保留原观察，写明什么新证据能推进。 |

每项记“实际分支、可省动作及次数、前提、证据”。看到可省工作或定位到可信差距，进③。只有热点线索，先作能区分解释的核查。当前路径已足够直接，就标为“已具备”并列作保护。两版都做同一份重复工作也可以成为改善机会，归因原有退步仍要有相应对照。

### ③ 按机制归并，选择可独立撤回的试验

从实际调用关系找出共享成本的位置。满足同一前提、能省同一动作、退出条件相容才归为同一方案。进入同一函数却走另一分支的调用者单独判断。分别列出能受益的目标和只可能付出额外判断、分配或锁开销的旁路。

选一个代表负载、一个打破前提的反例和最可能受损的相邻入口。**确认目标用例走到本次改动。** 写明哪个输入从哪个实际入口会走到要优化的路径。输入、配置和源码已能确定时直接引用，仍有疑问才在计时外做一次最小核查。若现有用例只走相邻路径，保留它们作为保护项，并在获准测量时补一个命中目标路径的用例。目标收益依据命中用例的实测判定。

**用户做一次操作，这项改动能省几次工作？** 如果每处理一项都能省一步，而一次调用还有固定开销，先从使用样例或运行记录核对一次调用通常处理多少项。若数量可能改变改动的去留，在同一入口选单项和一个有依据的批量，每种规模分别比较原版与候选。只支持单项的入口就测单项。典型批量未知时，写明所选规模的依据或假设，结论限于已测规模。计时循环里多次重复单项调用，测到的仍是单项场景。

写明试验固定什么、只改什么、预期少做几次、哪项结果会改变选择。按要省的这一步工作，查原方案记录和最近的类似补丁，核对已验证的做法与最接近的失败试验。相同方案直接沿用原结论，重开要指出新机制、新前提或新证据。按每次绝对成本、已知业务频率、影响范围、能否解开其他已证收益的冲突，以及试验和复验成本排序。收益上限太小时转向算法、数据布局、调用方式或其他主项。

**耗时试验前的子 Agent 核查（仅限第一轮第③步）。** 准备投入一轮耗时试验时，若目标用例是否命中改动、或共用这段代码的哪种用法可能变慢仍未查清，且答案会改变用例选择、改动范围或候选去留，就在原预算内启动一名子 Agent。派发前说明主 Agent 可以同时推进哪项独立工作。若必须等答复，把交接、等待和核对都计入成本，只有能避免的误测或返工值得这次等待时才派发。

- **核对启动配置。** 子 Agent 必须使用与当前主对话完全相同的模型和推理强度。使用工具明确保证同时继承这两项设置的方式，或在派发配置中逐项指定主对话的实际值。无法保证两项一致时，由主 Agent 自行完成核查，并在原记录中注明原因。
- **交给它一个能查证的问题。** 提供当前版本、拟改位置、真实输入、测试用例和已有证据。子 Agent 只读源码和已有记录，从实际入口追踪目标用例，核对它走到哪段代码、哪个相邻用法也经过这里并可能受损。返回判断、具体证据位置、尚未确定之处和最小下一步。
- **主 Agent 决定怎么试。** 核对证据后，在同一份记录里写明按原方案试验、换用例、补相邻保护、收窄改动或撤回的理由。出现分歧时，优先核查能区分两种解释的证据。实测由主 Agent 统一安排，避免其他工作与正式计时争用资源。

开始前确定有限的核查动作、检查点、剩余额度和停止条件。获准实施且完整动作装得进余额时进④。只获准分析时在这里留下明确候选、验证方法及不同结果应采取的行动。

### ④ 隔离改动，建立公平对照，决定处置

比较候选前，先核对已有证据是否适用于当前版本和场景。证据足以回答本次取舍，就按下方规则决定去留。需要新数据或结果难以解释时，用 `$noise-resilient-benchmarking` 核查，沿用原预算和剩余复测次数。

从已核实的直接父版做一个可重建、可回退的改动。先从正常入口检查原输出、精度、顺序、异常、回调、资源所有权和并发保证。失效时走原有正确路径。修复影响正确性的差异后，再比较性能。

**项目已有测量协议时**，保留其计时边界、质量门槛、顺序与进程配额、统计量、独立轮、有限补证条件和已用次数。只核查受环境、代码或输入变化影响的部分。已批准的差异和例外限于原工件、条件和权限，保留原严格成绩。

**项目没有成熟协议时**，先用低成本试跑建立以下最小对照，再据结果决定是否扩大。

1. 固定输入或数据来源、规模和分布、实现与参照身份、环境、冷热状态和计时始终点。实际交付方式需要的启动、解析、分配、消费、等待或析构按该入口的语义计入。先验证两方完成相同工作并交付同义结果。
2. 用短预试检查时钟分辨率、批长与环境波动。小到无法区分的单次调用可用相同批量放大，两方使用相同工作量。选取能覆盖主要使用方式和最可能受损边界的样本，预先写定测哪些、怎样判断、何时停止。校准与正式结果分开。
3. 让原版与候选在相近条件下交替或平衡顺序，保留各方完整结果和独立复核。某个配对无效时，按事前规则重取完整组。记录绝对耗时、配对变化、各轮方向和波动。负载型服务同时记录到达、失败和未完成工作，输入分布变化要单列。
4. 只有充分、可比的证据才判为达标、改善或可信退步。不能取两方各自最快成绩拼接，也不能反复换指标直到看见提速。动作计数用于归因，真实入口的成绩用于交付。

#### 核查异常退步的原因

以下核查沿用原协议、剩余预算和复测额度。把诊断结果写回原比较行，保留原实测判定和保护要求。

- **改动机制不同的候选反复在同一场景出现相近异常，且归因会影响选版时**，让同一工件分别充当基线和候选，沿用原比较两侧各自的安装、加载和运行方式。若同版也出现方向和幅度相近的差距，将这项退步的源码原因记为未明。若同版未复现，仍需用能区分原因的对照检验具体改动。
- **准备用采样解释退步时**，先核对采样期间是否重现原来的变慢。捕获慢态后，用当时的调用栈或热点检验假设。若只采到正常状态，热点可作独立优化线索，这项退步的原因仍记为未明。

#### 统计未明与覆盖缺口怎样补证

遇到未决项，先在原比较行写下 **影响哪个决定｜最小补证动作｜何时停止或重开**。覆盖缺口按事先登记要测的范围统计，包括缺少的场景、完整配对或独立轮。有合格的可比测量、仍然无法判定的门槛记“统计未明”（U）。某轮已测、另一轮缺失时，两种事实分别保留。

优先补关系到已确认目标、受影响入口的硬保护或最终工件验收的证据。对可选项，先回答“如果守线会保留什么？如果证实超线会修正或撤回什么？”两种结果都不改变选版时，写清受限的声明即可。共用实现有功能证据、原计划未安排单项计时的，另列“无独立计时”，不计入覆盖缺口总数。

| 情况 | 最小动作 |
| --- | --- |
| 缺规定的配对组或独立轮 | 核对工件与配置。保留有效组，按原顺序只补缺少的完整配对。缺独立复测时，用协议规定的独立进程或环境完成该轮。 |
| 计时分辨率不足、质量检查失败，或工件、运行条件错配 | 核对实际加载的工件、计时边界、双方批长与冷热状态。先纠正失效原因，需要时才在原权限内校准受影响的场景。工件或配置改变后，用新身份完成所需对照，旧样本保留在原记录。 |
| 输出语义或工作量不同 | 核对契约。违反契约就先修正确性。已批准的差异另找同义参照，找不到就标“不可比”。若已有确认的绝对目标，仍可用当前工件的有效实测单独判断。 |
| 规定数据已齐，区间跨过适用门槛或不同轮次方向冲突 | 查各轮区间、绝对差及预定分组，按原协议逐档判定。只为能改变决定或合同必验的门槛做有区分力的对照或预定复测，保留全部合格快慢值。若另一档已足以作决定，未明档又无单独必验要求，就依已明确的一档行动，另一档保留 U。 |
| 收益方向和价值已证实，只有提速幅度不稳 | 按下方候选处置表执行用户的开场选择，保留原严格判定。缺覆盖、方向未明或真实退步各按其自身证据处理。 |

**补测前写明停止条件。** 记下哪种结果足以作决定、仍未明时如何选版，再核算该动作与收尾所需的时间和次数。已有证据足以判定适用门槛，就按原规则回填并停测。原额度内仍有办法补齐必需证据或改变选版时，执行其中最小的一项。额度用尽或办法已尽时，保留新旧证据及重开条件。必验保护仍无法确认时，隔离受影响的改动并复验其余组合，或保留最近已验版本。若任务的必要条件仍缺，按实际范围部分交付，其他可独立推进的项继续。

#### 两个阶段共用的候选处置表

| 得到的证据 | 实际行动 |
| --- | --- |
| 目标可信改善，原协议的稳定性要求及必要保护均满足 | 记录适用条件、实际工件与回退点，在授权范围内晋级为当前工作版本。正式验收沿用目标的确认状态。扩展到其他已确认命中同一条件的能力时，补该处必要验证。 |
| 收益方向持续为正，只有收益幅度的稳定性未达标 | 核对完整正式测量、独立复测及预定分组和运行顺序均支持同向收益，测量质量合格，保守收益超过测量误差、达到事先约定的有意义收益，且必要保护均通过。按开场答复逐项处置。选“接受”且证据齐备时，优先纳入最终组合复验，最终工件仍满足这些条件才保留。选“不接受”时，从可采用候选和最终组合中排除这一未达标的改动，保存原始结果。答复待决定或证据尚缺时，单列对应缺口。 |
| 对父版变快，对固定基线或绝对目标仍有差距 | 分别列出本次增量和未追回的绝对差距。有独立价值且符合本地采用条件的部分可以保留，剩余问题回填。 |
| 目标快了，其他规模、调用者、运行模式或资源指标可信退化 | 查成本从哪条共享路径传出。尝试缩小适用范围或拆开改动，同时复验原收益和受损项。仍有不可接受代价则撤回该部分，保留其余可共存收益。必要保护的改变只能按已有权限逐项决定。 |
| 正确性、安全、生命周期或异常契约受损 | 停用该写法，保存最小反例。修复保护并通过对应验证后才重新比较性能。 |
| 同义对照的精度足以排除有价值的收益，或证实更慢 | 停止这一写法，保存排除依据和适用范围。有独立且能改变决定的假设时转查下一条。 |
| 只有源码推断、历史候选收益，或当前证据仍不确定 | 写明待验证的量、最小公平对照和恢复条件。区间仍允许有价值收益时保留未明。清楚说明“值得试”、已验证提速、已采用这三个状态。 |

两种选择都保留原严格判定（如“统计未明”）、各轮实测范围与最不利分组。按例外采用时，另记本次答复、所比较的工件、场景和条件。组合换版后用新工件的证据复核。若波动发生在用户要求保护的尾延迟、资源或错误率上，按该指标原有门槛处理。

#### 从已验证的优化寻找其他适用入口

第一轮首次验证一种做法有效时，在原方案记录里用一句话写清“在什么条件下，怎样省去了哪一步工作”。例如，输出格式已定，临时结果只用于最后一次复制，且能保留原有错误行为时，可以直接写入最终缓冲。关联已测的入口、工件和结果，也记下哪些用法失败或被撤回、为什么。若只测过多项改动的组合，单项起作用的原因仍记为假设。

沿①的清单主动找有同样成本的入口，包括由不同函数实现的路径。已经共用这项改动的，关联原方案，只补该入口缺的必要证据。原本就省去了这一步、前提不符或收益上限太小，就跳过这次匹配。仍有机会时，能用同一改动的入口共用一个方案。需要不同改法的，分别列为候选，引用同一思路。在原授权和剩余预算内按③、④验证目标和受影响的旁路，各入口按自己的实测报告收益。已判断的匹配只在条件或证据变化时重开。

### ⑤ 组合复验，选择一个版本

合格改动逐项进入可回退的工作版本。每次组合后复验主项、受影响的旁路和此前保住的收益。合包发生冲突时，先隔离并修正引入退步的路径。若它仍超出保护线，把能独立成立的改动放回上一个已验版本，复验后作为后续起点。尽可能把可共存的收益保留在同一个最终版本，按该版本的实测报告结果。更新原清单，继续②处理其他值得推进的能力。

**换版后的完整复验会明显压缩修正时间时**，按已观察到的构建、安装、完整复验和交付耗时倒推最晚换版时间。在此之前，先在拟选版本上测试少数一旦失败就会改变选版的“运行环境 × 公开入口”组合，给修正或回退留出时间。最终工件按原约定范围验收。全套验证能很快完成时，直接全验。

每次选定可交付版本时，依次核对以下四点。

1. **先守硬约束。** 核对必须通过的正确性、安全和资源、性能保护。已授权的单项例外写明边界和原判定。无合适新版本时交付上一个已验证的检查点，新增收益记零。
2. **再看主目标。** 在满足必要保护的候选中，按已经确认的主指标、代表负载及实际价值选择一个版本。用户给定、项目已批准、用户委托 Agent 制定的目标各记其来源。即使比起点快，只要还差用户要求的硬目标，就写出实际差距并继续获准的修正或部分交付。仅有推定口径时，报告相应条件下的实测改善和未经确认的偏好。
3. **处理接近或互有胜负的候选。** 证据能说明性能无实质差异时，优先已验证、简单、资源代价低且易回退的实现。数据精度不够时，保留未明。若一个版本缩短交互延迟、另一个版本提高后台吞吐，两者不能按现有授权排序，就保留已验检查点，同时用实际数字询问用户能接受多少互换。不能把未说明的业务权重当作采纳依据。
4. **冻结并读回。** 实际构建、安装或部署到获准的验证环境，从用户入口验证功能、性能与回退。对照项目已约定的必验项，逐项核实选定工件在适用环境中的执行记录和结果。漏跑或意外跳过的项在原范围内定向补验，未补齐的列为验收缺口，项目允许的跳过写明原因。分别报告相对起点、必要父版和原固定基线的结果。一个新版本的成绩只归到与它匹配的证据。没有可靠增益时如实报告原版或局部结果，不能宣称全项目普遍变快。

试验候选刚引入的退步就在本轮按④收窄、修正或撤回，再复验受影响的入口。第一轮完成时，范围已逐项对账，选定版本可用、可回退，并已完成本轮必验的实测。源码能证明共享实现覆盖，某一入口的速度要有该入口的测量。选定工件仍有已测出的差距时，带着结果进入下述分流。本轮必验条件尚缺时标明部分结果与恢复点。项目验收与正式发布沿用各自权限。

## 第一轮选定版本后怎样分流

依据选定工件在真实入口的结果，逐场景判定。用户带来的既有第一轮也沿用同一条件。

| 选定版本上的证据 | 在当前记录中怎样处理 |
| --- | --- |
| **确认退步。** 按原协议，同义输入、输出和工作量下，选定版本相对适用基线发生可信退步。 | 标记“相对退步”，关联基线、工件、场景和实际失败的轮次。跨多档门槛的一条比较只计一次。 |
| **确认的目标缺口。** 选定版本的实测未达到用户给定、项目已批准或用户明确委托制定的目标，哪怕已经比起点快。 | 标记“目标未达”，记目标来源、判据、实测值和差距。绝对目标可由本版实测判定，相对目标须核对约定参照。只有同时证实相对退步时才计入回归数。两类同时命中共用同一场景 ID。 |
| 只有统计未明、覆盖缺口或工件身份不符。 | 留在主流程，按④判断它影响哪个决定以及怎样补证。其他场景已有确认差距时可先交接那些场景。 |
| 目标尚待确认，或某项只是排名靠后。 | 按①核对目标及来源，再依据实际测量判定。 |
| 输出语义或实际工作量不同。 | 按④核对契约和同义参照，保留该组比较的实际状态。 |

**只有选定版本实测确认退步或未达已确认的目标，才转入慢项诊断。** 在原权限内有可推进的工作时，读取 [Diagnose Performance Gaps](../diagnose-performance-gaps/SKILL.md)（`$diagnose-performance-gaps`），带入对应场景和下表中的记录。收到诊断结果后，回到本入口决定试验、组合复验和交付。两类都为空、必要证据齐全且所需业务取舍已决时，直接进入最终交付。尚欠必验证据时先有限补证。执行边界已到时据实交付阶段结果和恢复点。

### 两个阶段共用的记录

沿用同一份项目记录、稳定的场景与方案 ID，并交接用户对收益幅度稳定性的开场答复及适用范围。原总预算、累计已用时间、各项已用补证与复测次数、剩余额度和收尾预留随任务一起传递。切换文件、阶段、候选或版本时继续累计。

| 需要读回的内容 | 最少要能回答的问题 |
| --- | --- |
| 版本和权限 | 本轮起点、旧能力参照、新语义的适用参照、已验父版、第一轮选定版本及回退点各是谁？实际运行的构建、安装或部署能否核对？此次允许诊断、实施、测量和采用到哪一步？ |
| 目标的来源与确认状态 | 分别列出用户明确给定、项目已批准、用户授权 Agent 制定、推定待确认，以及尚未设置的目标。记入口、负载、主指标、阈值或对照准则、保护项及未决的业务取舍。确认过的部分与未确认的部分分别判定。 |
| 全范围清单 | 原规格分母和每个能力 ID 是什么？哪些直接改过、复用改动、原已具备、试后保留原状、待补证或未查？各自关联哪个出口、场景 ID、方案和证据？ |
| 每条比较 | 稳定的场景 ID、入口、输入规模／分布、运行条件、所用参照与候选、协议及结果位置。保留各轮两侧同期绝对值、差值、相对变化和适用区间、门槛及原严格判定。另记业务结果是否等价、测量覆盖和质量。 |
| 尝试过什么 | 方案 ID、要消除的动作和适用条件、实测父版／候选、原目标和旁路结果、取舍或回退原因。属于特定版本的批准例外与原始判定分别保存。说明什么新事实足以重开。 |
| 还能做多少 | 原总预算、累计有效时间、明确暂停、截止或阶段上限、各问题已用补证／修正／复测额度、剩余量、必要收尾成本及下一个可完成的动作。 |

**候选换版后的第一件事。** 保存旧版本、旧行与旧判定。将新工件回连到受其影响的目标和保护项，优先复验新成本可能传播的调用者。输入、工件、环境、协议和计时范围确实适用的证据才可计入新结论。项目已有的补证和复测用量继续累计。若组合撤回，恢复上一个可用版本和与其匹配的证据。一个新版本或一个旧方案的新名称，本身不足以重开已结算的调查。

**收到慢项结果后。** 已结算的行动链写明“有方案”或“当前无方案”及证据，未查范围与恢复条件另列。对尚待试验的候选，在实施授权与余额内走④隔离验证、⑤组合复验。已有与该工件和协议匹配的完整验证就直接引用，按实际结果记录采用、收窄、撤回或仍待补证。仅需分析时交付建议与停止条件。可推进的独立场景继续处理，最终由本入口汇总一个交付版本及其限制。

## 最终向用户交付什么

按本次任务的授权和实际完成范围核对以下五项。

1. **版本与操作。** 实施交付要指明唯一选定的已验版本及回退点，给出可直接使用、复现和回退的命令。仅作分析时，标明查的是哪个版本，给出建议试验和停止条件。
2. **目标与验证范围。** 写明主目标由谁给定、沿用或确认，哪些仍是建议。列出实际验证的入口、平台、代表负载和必须守住的约束。
3. **逐项结果。** 对照原清单区分实测改善、共享实现覆盖、原已具备、部分追回、仍慢、证据不足与未查完。标清每个改法是候选、已验证提速还是已进入交付版本。
   从最终工件的实测明细反查清单，按实际输入和入口，把每条比较挂回它直接测到的能力。仅作旁路保护或属于范围外的，注明用途。核对后再标“无独立计时”。漏挂的已有结果直接补回原行。
   保留原判和补证记录。同一统计项在用户报告和已有的机器汇总中，都从纳入合格补证后的有效明细按相同分母复算。一条比较可关联多项能力，统计比较总数时只计一次。采用例外单列，保留严格判定。
4. **收益与代价。** 给出选定工件在用户实际入口的绝对耗时或其他主指标、比较参照、配对变化与独立复核结果。列出受影响的其他入口和资源代价。遇到只有收益幅度不稳的项时，并列报告用户选择、原严格成绩和实际取舍。其他已获批准的例外也各自保留原判定。
5. **预算与续接。** 列出时间和复测次数的已用量与剩余量。分别报告当前工件的严格 U 总数、计划内覆盖缺口总数，以及两类中各有多少项实际阻挡采用或完整验收。注明计数单位和适用门槛。依开场选择采用的幅度例外保留在严格 U 总数中。对阻挡项点名场景、影响的决定和最小恢复动作，汇总受影响场景时按 ID 去重。对其余未查完的范围留恢复点，未决业务取舍列出具体收益与代价。

**完成与停止要分别表述。** 没有可信退步、没有未达的已约定目标、没有必要证据缺口，且所选版本满足本次任务目标时，可以直接完成。只剩无进一步价值的调查，或授权、时间、次数已到边界时，停止新增试验，交付已验证的版本和实际限制。未设目标或待用户确认时，报告测量事实、采用依据及待定项。没有有据可交付的新增提速时，以最近已验版本和新增收益为零如实结算。

若主要目标仍有明显差距，又打算提前收尾，针对最值得查的一项问自己“还有哪个未做过的小核查能改变下一步决定？”有价值、已获授权，且连同可能的修正、必要复验和交付都在余额内，就继续。否则在该项原记录写明停止依据，有具体重开条件时一并留下。

## 内置案例

### 一处改动能覆盖哪些类型，哪些收益可以保留

SQLAero 从 `d9d0563` 起步，盘点 114 种类型，原预算 48 小时，追加 10 小时。本地交付的 6 个 Python ABI 安装包来自同一版本 `ab794d1`。下例的 1%／5% 分档属于该项目，候选试验的收益归属各自的比较工件。

| 情况 | 改变判断的证据 | 行动 |
| --- | --- | --- |
| 短 SQL 二进制写出时，每个字节可用一次查表得到两个十六进制字符。 | Python `bytes` 和四类 Arrow 二进制数组共用写入器，Arrow 的各条路径仍按自身布局检查偏移、宽度或视图范围。最终包对起点有 `bytes` 和 Arrow `BinaryArray` 的独立计时，其余三类有共享实现与功能覆盖证据。 | 五类都登记实现覆盖，只给有直接计时的两类报告相应场景的实测收益。 |
| 公开投影和数据库取行共用元组组装。 | CP314 的千行四列 NumPy 投影两轮耗时均减少超过 17%，两套 MySQL 的百行取数却均增加超过 10%。恢复取行的原组装、仅在投影复用缓冲后，对同一参照复验，投影仍省约 15%，两套百行取数均回到 1% 保护线内。 | 保留收窄后的改动，在最终组合上复验两个入口。 |
| 通用迭代器改动让千项 `dict.items()` 变快。 | CP314 候选对直接父版，目标两轮耗时均减少约 22%，普通千项字典却均增加约 24%，集合也越过保护线。 | 撤回这项共用改动，保存目标收益与旁路失败。能隔离特定调用者的新机制出现时，再开对应试验。 |

### 一档未明，另一档已经能决定下一步

SQLAero 较早的 EC8 工件对 F0 测密集转义时，原生 JSON 出口两轮的耗时增幅区间都约为 4.8%～5.2%。两轮都跨 5% 线，也都明确超出 1% 线。如果本次选版适用 1% 保护线，就按已确认的退步修正或隔离，5% 那一栏保留 U。只有另一项决定或单独的必验要求依赖 5% 结论时，才继续判断该怎样补证。

### 同一组结果，用户给的目标怎样改变选版

这是影像服务的模拟数据。使用相同的到达轨迹和初始缓存，每轮一分钟，表内依次列出两轮结果。

| 版本 | 成功预览 p99（ms） | 后台完成量（件／分钟） |
| --- | --- | --- |
| 基线 | 278／285 | 120／121 |
| 甲 | 145／150 | 106／107 |
| 乙 | 323／320 | 175／172 |

- **用户已给目标。** 要求预览 p99 不超过 160 ms、后台每分钟至少 105 件，甲在两轮都满足这两个指标。核对正确性、失败率、期末积压和资源保护后可选甲。缺少必验的积压证据时，保留为待补验候选。
- **用户只说“高峰快一点”。** 先查已批准的标准和用户是否委托 Agent 决定优先级。若两者都没有，甲偏向预览，乙偏向后台，此时保留已验基线，只问会改变选版的问题。相对基线，甲每分钟少完成 14 件后台任务，换来两轮预览 p99 分别缩短 133 ms 和 135 ms，用户是否接受？只给了内存上限时，先按上限筛选，再处理仍会改变选版的取舍。
- **没有硬指标也能交付。** 在演出排表示例中，用户只要求尽力提速。按需在一次调用内建立索引，避免空节目扫描整张曲库。独立输入验证了批量排表 API 的改善，命令行结果仍有波动。必要保护满足且已有实施授权时，交付同一个版本，分别报告批量收益、命令行的不确定性与内存代价。
